## 1. 수정 우선순위

### R1. 스페인 교환 거래에서 수수료 포함 여부에 따라 같은 거래의 세액이 달라짐 — 높음

- 근거: 정의서 4절의 `sell_fees_included`, `swap_given_value`; `src/coin/taxes.py:133~138`.
- 처분 총액과 원래 자산 시가를 비교한 뒤, 포함 체크가 있으면 수수료를 전혀 차감하지 않는다. 수수료 차감 후 처분액과 차감 전 원래 자산 시가를 직접 비교하는 경우가 발생한다.
- 재현: 스페인 암호자산 교환, 취득원가 10,000 EUR, 받은 자산 시가 20,000 EUR, 원래 자산 시가 20,000 EUR, 처분 수수료 1,000 EUR, 기타 저축소득 0.

| 입력 방식 | 처분 총액 | 수수료 포함 체크 | 계산된 순처분액 | 계산된 이익 | 예상세액 |
|---|---:|---|---:|---:|---:|
| 수수료 별도 | 20,000 | false | 19,000 | 9,000 | 1,770 |
| 수수료를 총액에 반영 | 19,000 | true | 20,000 | 10,000 | 1,980 |

- 동일 거래를 표현했는데 두 번째 입력은 시가 비교에서 차감된 수수료가 사라진다. 기존 `test_fee_inclusion`과 `test_spain_progressive_and_swap`은 각각의 기능만 확인하여 조합 오류를 놓친다.
- 권고: 시가 비교는 수수료 차감 전 금액끼리 수행하고 그 뒤 수수료를 한 번만 반영하도록 계약을 명확히 한다. 체크 시 수수료가 읽기 전용인 현재 화면에서는 차감 전 가액 복원에 필요한 정보가 부족할 수 있으므로, 교환일 때 총액·시가·수수료 입력 의미를 함께 정리해야 한다. 이 보고서의 결과는 입력 정합성 재현이며 새 세법 해석을 확정한 것이 아니다.

### R2. 일본 암호자산의 소득 누락 분기에서 해외 납부세액을 버림 — 중간

- 근거: 정의서 5.1·5.3의 `foreign_tax`; `src/coin/taxes.py:285`, `src/coin/taxes.py:313`.
- 재현: 일본 암호자산, `other_income=''`, `foreign_tax='100'`, 나머지 거래 입력은 유효하게 제공.
- 실제: `status='range'`만 반환하며 `foreign_paid`와 `taxCreditReview` 안내가 없다. 미국의 동일한 범위 추정 분기에서는 납부액과 검토 안내가 남는다.
- 원인: 일본은 소득 누락 시 공통 납부세액 처리 전에 바로 반환한다.
- 권고: 세액 범위 응답에도 공통 해외 납부세액 후처리를 적용한다. `test_foreign_credit_not_assumed`에 일본 소득 누락 사례를 추가한다. 중국 차단·특수 거래·NISA처럼 입력 자체가 숨겨지는 경우와는 구분한다.

### R3. 규칙 데이터의 설명용 값이 실제 적용 조건과 다름 — 중간

- 근거: `src/coin/data/tax_rules.json`의 국가·자산별 `exemptionType`, `exemptionAmount`, `holdingPeriodRule`, `brackets`와 `taxes.py`의 국가별 분기.

| 레코드 | 데이터 값 | 정의서·현재 계산과의 차이 |
|---|---|---|
| 한국 국내 주식 | `exemptionType='deduction'`, `exemptionAmount='2500000'` | 정의서에서는 남은 공제액을 숨기며 코드도 이 공제를 사용하지 않고 시장별 거래세를 계산 |
| 독일 주식 | `holdingPeriodRule='over_calendar_year'` | 정의서·코드의 1년 보유기간 분기는 독일 암호자산 대상. 독일 주식은 보유기간으로 세액을 분기하지 않음 |
| 일본 주식 | 최상위 `brackets`에 5~45% 누진 구간 | 주식 계산은 `stockIncome` 등 고정 세율을 사용하며 이 구간은 암호자산 계산용 |

- 해당 설명용 키들이 현재 세액 분기를 직접 결정하지 않아 즉시 잘못된 세율이 적용되지는 않는다. 그러나 데이터를 규칙의 단일 근거로 사용하면 잘못 해석할 수 있다.
- 권고: 각 자산·거래구분에 실제 적용되는 메타데이터로 정리하거나, 적용하지 않는 설명 필드는 제거한다. 현재 계산용 파라미터와 설명용 필드를 구분하고 상호 일치 검증을 추가한다.

### R4. 중복 규칙과 중복 세율 정보 — 유지보수

- 26개 규칙의 `(국가, 연도, 자산, 국내/해외)` 키는 모두 고유하다. 중복 키로 덮어쓰는 문제는 없다.
- 하지만 `domesticForeignType`만 제외하면 국내/해외 13쌍이 전부 동일하다. 한국·중국 주식처럼 실제 처리는 다르지만 동일 파라미터 묶음을 복제한 경우도 포함한다.
- 일본·스페인의 최상위 `brackets`와 `surtaxRules.brackets`에도 동일 내용이 반복된다. 계산기는 후자를 사용한다.
- 권고: 공통 파라미터를 공유하고 조회 시 조합별 레코드를 생성하거나, 현 구조를 유지한다면 복제값 일치 검사를 둔다. 국내/해외 조회 키는 화면과 API가 사용하므로 레코드를 단순 삭제해서는 안 된다.

## 2. 계약 또는 명세를 명확히 해야 할 사항

### 화면 기본값과 직접 API 요청의 기본값

- 정의서의 수수료 포함 기본 true 및 국내주식 통화 자동 적용은 UI에서 수행된다.
- `taxes.py`의 `flag()`는 누락된 체크 값을 false로 처리하며, `exchange_rate()`는 국내주식이라도 통화가 누락되면 오류를 반환한다.
- 정상 화면은 체크값과 자동 통화를 보내므로 현재 화면 기능의 누락은 아니다. 외부 API도 동일한 기본값을 지원하려면 API 계약을 별도로 명시해야 한다. 정의서에 UI 전용 기본값이라는 설명을 추가하는 방법도 있다.

### 같은 취득일의 FIFO 순서

- `taxes.py:148`의 `sorted(parsed)`는 날짜가 같으면 수량, 그 다음 원가까지 비교한다. 입력한 행 순서를 유지하는 정렬은 아니다.
- 날짜만 받는 현재 정의서는 동일 날짜의 서로 다른 취득분 순서를 정의하지 않았다. 부분 처분 시 원가에 영향을 줄 수 있으므로 ‘동일일 입력 순서 유지’ 또는 ‘동일일 합산’ 등 정책을 정하고 검증해야 한다. 확정된 정의서 위반보다는 명세 공백이다.

### 숫자 검증 주석

- `taxes.py:23`은 ‘24자리 이내’라고 설명하지만, 실제로는 문자열 길이·절댓값·소수 지수 범위를 검증하고 총 유효숫자 24자리 제한은 따로 검사하지 않는다. 문서화된 숫자 범위와 주석을 맞출 필요가 있다.

## 3. 일치 확인 및 검토 한계

- 지원 조합: 6개국 2026년 및 한국 암호자산 2027년, 총 26개 고유 규칙.
- 한국 암호자산 2026년·일본 적격 NISA의 최소 입력 비과세 응답, 특수 거래 우선 처리, 중국 암호자산 검토 필요, 독일 연간 손익 확인, 국가별 기본 과세 분기는 정의서와 대체로 일치한다.

- 최신 법률 검증·실제 브라우저 시각 검증은 수행하지 않았다. 실행은 기존 Python 테스트 및 별도 재현 요청으로 한정했다.
